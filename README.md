# 📖 พจนานุกรมภาษาถิ่นไทย (Thai Dialect Dictionary)

🔗 https://fluk17.github.io/phasa-thin/

> Web Application สำหรับค้นหา รวบรวม และเปรียบเทียบภาษาถิ่น 4 ภาคของไทย (กลาง, เหนือ, อีสาน, ใต้) แบบประมวลผลเร็ว รองรับการใช้งานสมบูรณ์แบบทั้งบนคอมพิวเตอร์และโทรศัพท์มือถือ

---

## 🎯 วัตถุประสงค์โปรเจกต์ (Project Overview)

โปรเจกต์นี้พัฒนาขึ้นเพื่อแก้ปัญหาความซับซ้อนในการค้นหาและเปรียบเทียบคำภาษาถิ่นไทย โดยสร้างฐานข้อมูลกลางที่เชื่อมโยงคำภาษากลางและคำถิ่นแต่ละภาคเข้าด้วยกันอย่างเป็นระบบ พร้อมระบบกรองข้อมูลหลายมิติ (Multi-filtering) และป้ายกำกับสถานะความถูกต้องของข้อมูล (Data Verification Status)

### 🌟 จุดเด่นของระบบ (Key Features)
- **การค้นหาแบบสองทาง (Bi-directional Search):** ค้นด้วยคำภาษากลาง หรือ คำภาษาถิ่น ได้ผลลัพธ์ทันที
- **การกรองข้อมูลตามภาค (Region Filtering):** กรองผลลัพธ์ตามภาค (กลาง/เหนือ/อีสาน/ใต้)
- **ระบบดึงข้อมูลแบบ Dynamic (Supabase Integration):** ดึงข้อมูลคลังคำผ่าน REST API ที่ Supabase สร้างให้อัตโนมัติจากตาราง PostgreSQL โดยเรียกตรงจากฝั่งเบราว์เซอร์ด้วย supabase-js ไม่ต้องมีเซิร์ฟเวอร์กลาง
- **Mobile-First Responsive Design:** ออกแบบด้วย CSS Grid/Flexbox รองรับหน้าจอเล็กสุด 320px พร้อมจัดการระยะขอบปลอดภัย (Safe-area) สำหรับอุปกรณ์ iOS

## 🏗️ สถาปัตยกรรมระบบ & เทคโนโลยีที่ใช้ (Tech Stack)

* **Frontend:** HTML5, Modern CSS3 (CSS Variables, Flexbox, Grid, Media Queries), Vanilla JavaScript (ES6+ Fetch API, DOM Manipulation)
* **Backend / Database:** Supabase (PostgreSQL + REST API ที่สร้างให้อัตโนมัติ + Row Level Security)
* **Hosting & Deployment:** GitHub Pages
* **Design & Responsive Standards:** Mobile-First Approach, Safe-Area Inset (iOS Supported)

## 🚧 แผนพัฒนาต่อ (Future Development)

รายการฟีเจอร์ที่ยังไม่ได้ทำจริงในระบบปัจจุบัน แต่ตั้งใจจะพัฒนาต่อ:

- **กรองข้อมูลเพิ่มเติมตามระดับภาษา/ชนิดของคำ/จังหวัด** นอกเหนือจากการกรองตามภาคที่มีอยู่แล้ว
- **การจัดเรียงตามหลักพจนานุกรมไทยแบบข้ามสระหน้า** (เ, แ, โ, ใ, ไ) เพื่อความถูกต้องทางภาษาศาสตร์ ปัจจุบันยังเรียงตามลำดับตัวอักษรมาตรฐานเท่านั้น
- **มาตรฐานการเข้าถึง WCAG Accessibility**
- **ระบบ CI/CD อัตโนมัติ** สำหรับ deploy ขึ้น GitHub Pages ปัจจุบันยัง deploy ด้วยมือ

## 📊 โครงสร้างข้อมูล (Data Schema - 14 Columns)

คลังข้อมูลถูกจัดเก็บในตาราง `words` บนฐานข้อมูล Supabase (PostgreSQL) ประกอบด้วย 14 คอลัมน์ (โครงสร้างจริงอยู่ที่ [`supabase/schema.sql`](supabase/schema.sql)):

| # | ชื่อคอลัมน์ (EN) | ความหมาย | ตัวอย่างข้อมูล | ห้ามว่าง |
|---|---|---|---|:---:|
| 1 | `id` | รหัสคำศัพท์ (uuid, ระบบสร้างให้อัตโนมัติ) | `f47ac10b-58cc-...` | ✅ |
| 2 | `central` | คำภาษากลาง | `มอง` | ✅ |
| 3 | `dialect` | คำภาษาถิ่น | `เบิ่ง` | ✅ |
| 4 | `region` | ภาคที่ใช้ (กลาง/เหนือ/อีสาน/ใต้) | `อีสาน` | ✅ |
| 5 | `province` | จังหวัดที่มีการใช้ | `ขอนแก่น,อุดรธานี` | ✅ |
| 6 | `reading` | คำอ่านออกเสียง | `เบิ่ง` | ✅ |
| 7 | `pos` | ชนิดของคำ (Part of Speech) | `กริยา` | ✅ |
| 8 | `level` | ระดับภาษา (ทางการ/ทั่วไป/กันเอง/หยาบ) | `ทั่วไป` | ✅ |
| 9 | `meaning` | ความหมาย | `ใช้สายตามอง` | ✅ |
| 10 | `example` | ประโยคตัวอย่างภาษาถิ่น | `เบิ่งหยังอยู่กะซั่น` | — |
| 11 | `example_th` | ประโยคแปลภาษากลาง | `มองอะไรอยู่งั้นหรอ` | — |
| 12 | `status` | สถานะการเผยแพร่ (ค่าเริ่มต้น `ยืนยัน` คำที่ส่งผ่านฟอร์มจะแสดงบนหน้าเว็บทันทีโดยไม่ต้องรอตรวจ) | `ยืนยัน` / `รอตรวจ` | ✅ |
| 13 | `note` | หมายเหตุ / ข้อมูลภาษาศาสตร์เพิ่มเติม | `อีสานใช้คำเฉพาะคือ เบิ่ง` | — |
| 14 | `created_at` | เวลาที่บันทึกคำนี้ (ระบบสร้างให้อัตโนมัติ) | `2026-08-02 10:15:00+07` | ✅ |

## 📁 ไฟล์ในโปรเจกต์

โปรเจกต์นี้เป็น repo เดียว ไม่แยก backend ทุกหน้าเว็บเป็นไฟล์ HTML เดี่ยวจบในตัว (ไม่มีโฟลเดอร์ `css/` หรือ `js/` แยก, ไม่มี build step) ยกเว้นสคริปต์ SQL ที่แยกไว้ในโฟลเดอร์ `supabase/`

| ไฟล์ | หน้าที่ |
|---|---|
| `index.html` | หน้าค้นหาคำ (หน้าแรกของเว็บไซต์) |
| `all.html` | หน้าคำทั้งหมด จัดกลุ่มตามพยัญชนะไทย ก-ฮ พร้อมปุ่มกระโดด |
| `submit.html` | ฟอร์มเสนอคำใหม่เข้าระบบ |
| `about.html` | หน้าข้อมูลโครงงานและสถิติจำนวนคำ |
| `search.html` | หน้า redirect ไปยัง `index.html` (เก็บไว้เผื่อมีลิงก์เก่าอ้างถึง) |
| `supabase/schema.sql` | สคริปต์ SQL สร้างตาราง/policy/trigger — รันด้วยมือใน Supabase SQL Editor เท่านั้น ไม่ได้ deploy ขึ้น GitHub Pages |
| `data/template.csv` | แม่แบบคอลัมน์สำหรับเตรียมข้อมูลคำใหม่ก่อนนำเข้าระบบ |
| `data/words_seed.csv` | ข้อมูลคำเริ่มต้น (seed data) ที่นำเข้าตาราง `words` จริงในระบบ |
| `docs/ARCHITECTURE.md` | เอกสารสถาปัตยกรรมระบบ |
| `docs/DEVLOG.md` | บันทึกการพัฒนาและปัญหาที่พบระหว่างทาง |

## 🛡️ กฎตรวจสอบข้อมูล 4 ด่าน

เนื่องจากระบบนี้ไม่มีเซิร์ฟเวอร์กลาง (ดูเหตุผลใน [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)) การตรวจสอบข้อมูลก่อนบันทึกจึงกระจายอยู่คนละชั้น ดังนี้:

| ด่าน | ตรวจอะไร | อยู่ชั้นไหน | ข้ามได้ไหม |
|---|---|---|---|
| 1 | ช่องที่ห้ามว่างต้องกรอกครบก่อนกดส่ง | JavaScript ฝั่งหน้าเว็บ (`submit.html`) | ข้ามได้ ถ้ายิง API ตรง |
| 2 | คอลัมน์ที่ห้ามว่างต้องมีค่าเสมอ | คอลัมน์ `NOT NULL` ในตาราง (`supabase/schema.sql`) | ข้ามไม่ได้ |
| 3 | คำถิ่นเดียวกันในภาคเดียวกันห้ามซ้ำ | `UNIQUE (dialect, region)` ในตาราง (`supabase/schema.sql`) | ข้ามไม่ได้ แต่มีข้อจำกัด — ดู ARCHITECTURE.md |
| 4 | คำหยาบที่เลือกระดับภาษาผิด | Trigger `check_profanity()` (`supabase/schema.sql`) | ข้ามไม่ได้ |

ด่านที่ 1 เป็นแค่การช่วยเหลือผู้ใช้ (UX) เท่านั้น ส่วนด่านที่ 2-4 บังคับอยู่ที่ฐานข้อมูลจริง ต่อให้แก้โค้ดฝั่งหน้าเว็บหรือเรียก API ตรงก็ข้ามไม่ได้ รายละเอียดพร้อมโค้ด SQL จริงอยู่ใน [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)

## 🔍 การตรวจสอบคำที่ผู้ใช้ส่งเข้ามา

ระบบนี้เป็น **auto-approve**: คำที่ส่งผ่าน `submit.html` เมื่อผ่านกฎ 4 ด่านด้านบนแล้วจะถูกบันทึกด้วย `status = 'ยืนยัน'` และแสดงบนหน้าค้นหาทันที ไม่มีขั้นตอนให้ทีมงานอนุมัติก่อนเผยแพร่

ผู้ดูแลระบบตรวจสอบคำที่เข้ามาแบบย้อนหลังผ่าน Supabase Dashboard (Table Editor) แทน หากพบข้อมูลผิดพลาดหรือไม่เหมาะสมจะแก้ไข/ลบด้วยมือที่นั่น

เหตุผลที่เลือกออกแบบแบบนี้: ระบบไม่มีเซิร์ฟเวอร์กลางที่จะรันขั้นตอนอนุมัติ (คิว "รอตรวจ" ก่อนเผยแพร่, ระบบแจ้งเตือนผู้ดูแล) และไม่มีระบบ auth แยกสิทธิ์ผู้ดูแลออกจากผู้ใช้ทั่วไป การทำ manual approval ก่อนแสดงผลจึงต้องเพิ่ม backend ซึ่งขัดกับสถาปัตยกรรมที่ตั้งใจไม่ใช้เซิร์ฟเวอร์กลาง (ดูเหตุผลใน [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md))

## 🧑‍💻 การติดตั้งและทดลองใช้งานในเครื่อง (Local Setup)

1. Clone Repository นี้ลงเครื่องคอมพิวเตอร์:
   ```bash
   git clone https://github.com/fluk17/phasa-thin.git
   ```
2. เปิดโปรเจกต์ด้วยส่วนขยาย **Live Server** ใน VS Code แล้วเปิด `index.html` ผ่าน `http://localhost` (ไม่แนะนำให้ดับเบิลคลิกเปิดไฟล์ตรง ๆ เพราะเบราว์เซอร์บล็อกการเรียก fetch ข้าม origin บน protocol `file://` ทำให้ supabase-js เรียก API ไม่ได้และหน้าเว็บจะโหลดข้อมูลไม่ขึ้น) ไม่ต้องติดตั้ง dependency หรือรัน build step ใด ๆ เพราะทุกหน้าเรียก Supabase ตรงจากฝั่งเบราว์เซอร์
3. ถ้าต้องการแก้โครงสร้างฐานข้อมูล ให้เปิด [`supabase/schema.sql`](supabase/schema.sql) แล้วรันใน Supabase Dashboard > SQL Editor ของโปรเจกต์ตัวเอง (สคริปต์นี้ไม่ได้รันอัตโนมัติ ต้องรันด้วยมือ)
