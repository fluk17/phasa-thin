# บันทึกการพัฒนา (Devlog)

บันทึกการตัดสินใจและปัญหาที่พบระหว่างพัฒนา แบ่งตามแหล่งข้อมูลที่ใช้ 2 เฟส

---

## เฟส 1 — Google Sheets + PapaParse

### การตัดสินใจ

- เลือก Google Sheets เป็นแหล่งข้อมูลเพราะ deploy บน GitHub Pages ซึ่งเสิร์ฟได้เฉพาะไฟล์ static ไม่มีที่ให้รัน backend เก็บฐานข้อมูลจริง
- Google Sheets แก้ไขข้อมูลได้ง่ายสำหรับคนที่ไม่ถนัดเขียนโค้ด (ครู/นักเรียนในทีมแก้คำศัพท์ผ่านหน้าตาสเปรดชีตตรง ๆ ได้)
- ดึงข้อมูลด้วย PapaParse จาก CSV ที่ Publish to web ไว้ ทำงานฝั่งเบราว์เซอร์ล้วน ไม่ต้องมีเซิร์ฟเวอร์
- ล็อกโครงสร้างข้อมูลไว้ที่ 13 คอลัมน์ (`id`, `central`, `dialect`, `region`, `province`, `reading`, `pos`, `level`, `meaning`, `example`, `example_th`, `status`, `note`)
- สร้างหน้าค้นหา (`search.html`) รองรับค้นหาสองทาง (คำกลาง/คำถิ่น) และกรองตามภาค

### ข้อจำกัดที่นำไปสู่การย้ายมาใช้ Supabase (เฟส 2)

- Google Sheets ไม่มีการบังคับชนิดข้อมูลหรือกฎระดับคอลัมน์ ใครก็แก้ค่าในชีตให้ผิดรูปแบบได้ตรง ๆ โดยไม่มีอะไรเตือน
- ไม่มีกลไกกันข้อมูลซ้ำหรือกันคำหยาบในตัวเอง ต้องพึ่งการตรวจทานด้วยมือล้วน ๆ
- ไม่มีช่องทางให้ผู้ใช้ทั่วไปเสนอคำใหม่จากหน้าเว็บได้จริง (ต้องเข้าไปพิมพ์ในชีตเองเท่านั้น) — `submit.html` ในช่วงนี้ยังเป็นไฟล์เปล่า

---

## เฟส 2 — Supabase (PostgreSQL)

### การตัดสินใจ

- ย้ายฐานข้อมูลมาเป็น Supabase (PostgreSQL) เพื่อได้ column constraint, unique constraint และ trigger มาบังคับกฎที่ Google Sheets ทำไม่ได้ (ดูรายละเอียดใน [`ARCHITECTURE.md`](ARCHITECTURE.md))
- ยังคงไม่มี Node.js/Express เหมือนเดิม — logic ทั้งหมดที่เคยคิดว่าต้องมี backend ย้ายไปอยู่ใน RLS policy และ database trigger แทน
- เพิ่ม `submit.html` เป็นฟอร์มจริงหน้าแรกที่เขียนข้อมูลกลับเข้าระบบได้จากฝั่งผู้ใช้

### ปัญหาที่พบระหว่างย้ายระบบ

**1. บั๊กตัวกรองภาคจากค่าหลายภาคในเซลล์เดียว**
คอลัมน์ `region` บางแถวเก็บได้มากกว่า 1 ภาคคั่นด้วยจุลภาค (เช่น `"อีสาน,เหนือ"`) แต่ตัวกรองภาคเดิมเทียบค่าแบบ exact match ทั้งสตริง (`region !== selectedRegion`) ทำให้แถวที่มีหลายภาคไม่ถูกจับคู่กับตัวกรองภาคใดเลย
วิธีแก้: เพิ่มฟังก์ชัน `splitList()` แยกค่าที่คั่นด้วยจุลภาคเป็นรายการ แล้วใช้ `.includes()` เทียบแทนการเทียบสตริงทั้งเส้น ใช้จุดเดียวกันทั้งใน `buildFilters()`, `applySearch()` และตอนสร้างป้ายภาคในการ์ดผลลัพธ์

**2. `relation "words" already exists` ทำให้ trigger ไม่ถูกสร้าง**
ตอนรัน `schema.sql` ซ้ำใน SQL Editor (หลังเคยรันบางส่วนไปแล้วก่อนหน้า) คำสั่ง `CREATE TABLE` แบบไม่มีการ์ดชนกับตารางที่มีอยู่แล้ว ทำให้ script หยุดกลางคันด้วย error และคำสั่งสร้าง trigger ที่อยู่ท้ายไฟล์ไม่ถูกรันเลย
วิธีแก้: ใส่ `IF NOT EXISTS` ในคำสั่งสร้างตาราง และ `DROP TRIGGER IF EXISTS ... ; CREATE TRIGGER ...` ก่อนสร้าง trigger ทุกครั้ง ทำให้ `schema.sql` รันซ้ำกี่ครั้งก็ได้อย่างปลอดภัย (idempotent) ไม่พังแม้ตารางจะมีอยู่แล้ว

**3. คอลัมน์ `id` แบบ `W0001` ชนกับ type `uuid` ตอน import**
ข้อมูลเก่าจาก Google Sheets ใช้รหัสคำศัพท์รูปแบบ `W0001`, `W0002` ฯลฯ แต่ตาราง `words` ใหม่กำหนดให้ `id` เป็น type `uuid` (สร้างค่าอัตโนมัติด้วย `gen_random_uuid()`) เมื่อนำ CSV เก่าเข้าตารางโดยยังคงคอลัมน์ `id` เดิมไว้ PostgreSQL ปฏิเสธทันทีเพราะ `"W0001"` ไม่ใช่ค่า uuid ที่ถูกต้อง
วิธีแก้: ตัดคอลัมน์ `id` ออกจากไฟล์ตอน import แล้วปล่อยให้ Supabase สร้าง uuid ให้ใหม่ทั้งหมด (แอปไม่ได้อ้างอิงค่า `id` เดิมที่ไหนอยู่แล้ว จึงไม่กระทบ logic ส่วนอื่น)

**4. เปิดจากมือถือแล้วเจอหน้าทดสอบเก่า**
`index.html` เดิมไม่ใช่หน้าค้นหา แต่เป็นไฟล์หน้าทดสอบเก่าที่ค้างมาจากช่วงเริ่มโปรเจกต์ ส่วนหน้าค้นหาจริงอยู่ที่ `search.html` (ตามเฟส 1) เมื่อมีคนเปิดเว็บจากมือถือด้วยลิงก์โดเมนตรง ๆ (ไม่ได้กดผ่านลิงก์ที่ระบุ `search.html`) เบราว์เซอร์จะเสิร์ฟ `index.html` เป็นค่าเริ่มต้นตาม convention ของ static hosting ทำให้เจอหน้าทดสอบเก่าแทนหน้าค้นหา
วิธีแก้: ย้ายเนื้อหาหน้าค้นหาให้กลายเป็น `index.html` โดยตรง แล้วทำ `search.html` เป็นหน้า redirect ไปยัง `index.html` แทน เพื่อไม่ให้ลิงก์เก่าที่เคยอ้างถึง `search.html` เสีย

### การทบทวนโค้ดก่อนขึ้น GitHub

**1. ข้อความหลังส่งฟอร์มบอกว่าทีมงานจะตรวจก่อนแสดงผล**
ข้อความสำเร็จใน `submit.html` เดิมบอกว่า "ทีมงานจะตรวจสอบก่อนแสดงผลในหน้าค้นหา" แต่คอลัมน์ `status` มีค่า default เป็น `ยืนยัน` อยู่แล้ว คำที่ส่งเข้ามาจึงขึ้นแสดงบนหน้าค้นหาทันทีโดยไม่มีการตรวจก่อนจริง ๆ ข้อความเดิมจึงสื่อสารพฤติกรรมของระบบผิด
วิธีแก้: เปลี่ยนข้อความให้ตรงกับพฤติกรรมจริงว่าคำเข้าระบบและแสดงผลทันที

**2. ลำดับการติ๊กภาคทำให้ UNIQUE constraint หลุด**
`getRegions()` เดิมคืนค่าตามลำดับที่ผู้ใช้ติ๊กเช็คบ็อกซ์ ทำให้ผู้ส่งสองคนที่เลือกภาคชุดเดียวกันแต่ติ๊กคนละลำดับได้ค่าคอลัมน์ `region` เป็นคนละสตริง เช่น `"เหนือ,อีสาน"` กับ `"อีสาน,เหนือ"` ซึ่ง `UNIQUE (dialect, region)` มองว่าเป็นค่าต่างกัน จึงไม่จับว่าซ้ำทั้งที่ควรซ้ำ
วิธีแก้: เรียงลำดับภาคตามลำดับคงที่ `["กลาง", "เหนือ", "อีสาน", "ใต้"]` ก่อน join ด้วย `,` ทุกครั้งใน `getRegions()`

**3. `create policy` ไม่มี `drop policy if exists` นำหน้า**
ต่อยอดจากปัญหาข้อ 2 (`relation "words" already exists`) ที่แก้ `create table` กับ trigger ให้รันซ้ำได้อย่างปลอดภัยไปแล้ว แต่ `create policy` ทั้ง 2 อันใน `schema.sql` (`words_public_select`, `words_public_insert`) ยังไม่มี `drop policy if exists` นำหน้า ทำให้รัน `schema.sql` ซ้ำยังพังด้วย error `policy "..." already exists`
วิธีแก้: ใส่ `drop policy if exists ...` ก่อน `create policy ...` ทั้ง 2 อัน ทำให้ `schema.sql` รันซ้ำได้ทั้งไฟล์อย่างปลอดภัย (idempotent)

### สถานะปัจจุบัน

- ตาราง `words` มีข้อมูลอยู่ 30 คำ
- `index.html` และ `submit.html` เชื่อมต่อ Supabase เรียบร้อยแล้ว
- `all.html` และ `about.html` ยังดึงข้อมูลผ่าน Google Sheets/PapaParse เดิมอยู่ ยังไม่ได้ย้ายมาใช้ Supabase
- ผ่านการทบทวนโค้ดรอบแรกแล้ว (2026-08-02)
